# team-tasks-service

REST API для задач внутри команд: регистрация и JWT, команды с ролями, задачи с историей изменений,
комментарии, SQL-отчёт по команде, кеш списков в Redis.

Стек: Go, MySQL 8.4, Redis 7.4, Docker Compose. Контракт — [`api/openapi.yaml`](api/openapi.yaml);
после запуска Swagger UI открыт на http://localhost:8080/docs/ (кнопка **Authorize** для токена).
Там описаны все методы, тела запросов, ответы и коды ошибок — README их не дублирует.

## Запуск

```bash
cp .env.example .env               # поменяйте секреты: openssl rand -base64 48
docker compose up -d --build --wait
curl -s localhost:8080/health/ready   # {"schema_version":1,"status":"ok"}
```

Compose поднимает `mysql` и `redis`, затем одноразовый `migrate` (применяет миграции и выходит), затем `api`.
Остановка — `docker compose down`, сброс вместе с данными — `docker compose down -v`.

Запуск API без Docker (зависимости — из Compose):

```bash
docker compose up -d --wait mysql redis
go run ./cmd/migrate up
go run ./cmd/api
```

## Конфигурация

Настройки берутся из переменных окружения и файла `.env` в текущем каталоге; переменная из команды
запуска важнее файла. `.env` не коммитится и не попадает в образ. Без обязательных переменных приложение
не стартует и пишет, каких не хватает.

| Переменная | По умолчанию | Что это |
| --- | --- | --- |
| `MYSQL_HOST`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE` | обязательные | MySQL |
| `MYSQL_PORT` | `3306` | порт MySQL |
| `REDIS_HOST` | обязательная | Redis |
| `REDIS_PORT` | `6379` | порт Redis |
| `REDIS_PASSWORD` | пусто | пароль внешнего Redis |
| `JWT_SECRET`, `CURSOR_SECRET` | обязательные | секреты подписи токенов и курсоров, от 32 байт |
| `JWT_TTL` | `1h` | срок жизни токена |
| `JWT_ISSUER`, `JWT_AUDIENCE` | `team-tasks-service`, `team-tasks-api` | claims `iss`, `aud` |
| `BCRYPT_COST` | `12` | стоимость bcrypt |
| `RATE_USER_PER_MINUTE`, `RATE_USER_BURST` | `120`, `20` | лимит запросов на пользователя |
| `RATE_AUTH_PER_MINUTE`, `RATE_AUTH_BURST` | `60`, `20` | общий лимит входа и регистрации на IP |
| `TRUST_PROXY_HEADERS` | `false` | брать IP из `X-Forwarded-For` (только за своим прокси) |
| `REQUEST_TIMEOUT` | `10s` | бюджет на запрос |
| `REDIS_TIMEOUT` | `100ms` | бюджет на операцию Redis |
| `MYSQL_LOCK_WAIT` | `5s` | ожидание блокировки в MySQL |
| `SHUTDOWN_TIMEOUT` | `10s` | ожидание активных запросов при остановке |
| `BREAKER_FAILURES`, `BREAKER_OPEN` | `5`, `30s` | circuit breaker перед Redis |
| `API_PORT` | `8080` | порт HTTP-сервера |

В Compose порты `MYSQL_PORT`, `REDIS_PORT`, `API_PORT` из `.env` используются и внутри сети, и для
публикации на хост. Контейнеры обращаются к базе по именам сервисов `mysql` и `redis`: `127.0.0.1` внутри
контейнера — это сам контейнер. Redis ограничен файлом [`deploy/redis.conf`](deploy/redis.conf):
`maxmemory 128mb`, `allkeys-lfu`.

## Миграции

Миграции goose лежат в `migrations/` и встроены в бинарник.

```bash
go run ./cmd/migrate up         # применить (повторный запуск безопасен)
go run ./cmd/migrate version    # текущая версия
go run ./cmd/migrate down       # откатить ВСЁ — удаляет таблицы и данные, только для локального сброса
docker compose run --rm migrate migrate version   # то же в Compose
```

## Примеры запросов

Полный список методов, тел и ответов — в Swagger UI (`/docs/`).

```bash
API=http://localhost:8080/api/v1

curl -X POST $API/register -H 'Content-Type: application/json' \
  -d '{"email":"ann@example.com","password":"password123","name":"Ann"}'
TOKEN=$(curl -s -X POST $API/login -H 'Content-Type: application/json' \
  -d '{"email":"ann@example.com","password":"password123"}' | jq -r .access_token)

curl -X POST $API/teams -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Platform"}'
curl -X POST $API/tasks -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"team_id":"<TEAM_ID>","title":"Подготовить релиз"}'
curl "$API/tasks?team_id=<TEAM_ID>&status=todo&limit=20&offset=0" -H "Authorization: Bearer $TOKEN"

# version обязательна; устаревшая — 409 task_version_conflict
curl -X PUT $API/tasks/<TASK_ID> -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":1,"status":"done"}'

curl $API/teams/<TEAM_ID>/stats -H "Authorization: Bearer $TOKEN"
```

## Как устроено

- **Конкурентные правки.** В `PUT` обязательна `version` — версия, которую клиент прочитал. Запись идёт
  условным `UPDATE … WHERE version = ?`; если кто-то успел раньше — `409 task_version_conflict`, ничего не
  теряется, клиент перечитывает задачу и повторяет. Изменение, запись истории и сброс кеша — одна транзакция.
- **Кеш.** В Redis на 5 минут кешируется только `GET /tasks`; ключ учитывает команду, фильтры и страницу.
  У команды есть ревизия в MySQL: создание или изменение задачи увеличивает её в той же транзакции, и все
  старые ключи команды перестают использоваться. Перед кешем всегда проверяется членство. При сбое Redis
  список читается из MySQL; после 5 отказов подряд circuit breaker на 30 секунд перестаёт ходить в Redis,
  затем одна проба.
- **Отчёт** — один SQL-запрос с CTE: задачи по статусам; топ-3 исполнителей по задачам, закрытым за
  последние 30 суток; среднее время закрытия в сутках; общее число комментариев к задачам команды.
  Комментарии считаются отдельно и не умножают остальные агрегаты.

## Допущения и ограничения сервиса

**ID.** ТЗ не задаёт тип ID: в таблице сущностей просто `id`, а `team_id=1` в примере URL — иллюстрация.
Все ID — UUIDv7: генерируются в Go, хранятся как `BINARY(16)`, снаружи — строки (регистр не важен, числа
дают 422). Это не связано с числовой `version` задачи. Порядок: задачи `id DESC`, комментарии `id ASC`,
история `task_version ASC`.

**Регистрация и вход.**
- Email не подтверждается (почты нет) — можно зарегистрировать чужой адрес. Для реальных пользователей нужно
  добавить подтверждение кодом или ссылкой.
- Refresh token нет: после истечения `JWT_TTL` пароль вводится заново, отдельно отозвать токен нельзя. В
  реальном проекте нужен refresh token с хранением хеша на сервере, ротацией и logout, чтобы access token
  оставался коротким, а пароль не приходилось вводить постоянно.

**Команды и роли.**
- Роли меняет только owner, admin — нет (403). Это вывод из ТЗ, а не наше решение: у owner право «менять
  роли» указано явно, в списке прав admin его нет, а фраза «admin не может удалить создателя или изменить его
  роль» — запрет, а не разрешение менять роли остальным.
- Исключение участников — функциональность сверх ТЗ, права на неё заданы нами: исключают owner и admin,
  owner исключить нельзя никому (согласуется с запретом из ТЗ «admin не может удалить создателя»).
- Приглашение принимает только `user_id` и сразу добавляет участника как member, без принятия; поле `role`
  — 422. Admin назначается отдельной сменой роли — так приглашением нельзя выдать роль owner. Поиска
  пользователей нет: приглашаемый сообщает свой ID из ответа регистрации или входа.
- Неучастник получает 404, а не 403: по ответу нельзя понять, существует ли чужая команда или задача.
- Исключение — в два шага: без `{"confirm_unassign": true}` при назначенных задачах — 409 с их числом.
  Подтверждение снимает все назначения в этой команде на момент запроса (с `version + 1` и записью в
  историю), затем удаляет участника; всё одной транзакцией. Повтор для уже исключённого — 204.
- Выйти из команды самому нельзя, передачи владения и удаления команд и задач нет. Состав и список команд
  отдаются без пагинации.
- `updated_at` есть только у `tasks`, как в ТЗ. Пользователи, команды и комментарии после создания не
  меняются, история только дополняется. Исключение — роль в `team_members`: время и автор смены роли не
  сохраняются. Если это понадобится, нужен `updated_at` в `team_members` или журнал изменений состава.

**Задачи.**
- `version` относится ко всей задаче: два клиента с одной версией не применят правки даже к разным полям.
  Автоматического слияния нет. Частичное обновление сделано через `PUT`, как в ТЗ.
- Право проверяется по каждому переданному полю, даже если значение не меняется: исполнитель, приславший
  `title` вместе со `status`, получает 403.
- Статусы фиксированы: `todo`, `in_progress`, `done`, переходы любые при наличии права. Переход в `done`
  ставит `closed_at`, выход из `done` очищает его.[^statuses]
- Курсоры сервер не хранит: клиент передаёт `next_cursor` как есть, токен подписан `CURSOR_SECRET`.
  Страницы не образуют общего снимка — изменения между запросами могут менять следующие страницы.

**Отчёт.**
- Считается по текущему состоянию задач, не по истории: переназначенная задача засчитывается новому
  исполнителю, исключённый участник выпадает из топа, повторно открытая задача перестаёт считаться закрытой,
  а после нового закрытия учитывается один раз. Расчёт по истории закрытий — возможная доработка.
- Окно 30 суток относится только к топ-3 исполнителей. Среднее время закрытия сознательно считается по всем
  закрытым задачам команды за всё время: в ТЗ окно указано только для топа.

**Кеш.**
- Ревизия списков хранится в MySQL, а не в Redis, ради корректной инвалидации из ТЗ: она растёт в той же
  транзакции, что и изменение задачи, поэтому сбой или circuit breaker Redis в момент записи не оставит в
  кеше устаревший список. Цена — чуть тяжелее запросы к MySQL: лишний `UPDATE` ревизии при каждой записи,
  а список читается в одной транзакции-снимке (членство, ревизия, `COUNT` в offset-режиме и страница
  последовательно), чтобы страница попала в кеш под ревизией того же момента. Проще было бы держать
  счётчик в Redis (`INCR` после commit), но тогда при частичном сбое Redis старый список отдавался бы до
  конца TTL.
- В Redis лежит `task.Page` как есть, без отдельного DTO: ключи JSON — имена полей Go-структур `Page` и
  `Task`. Переименование этих полей меняет формат кеша, поэтому вместе с ним нужно поднять версию в ключе
  `tasks:v1:…` (см. `listKey`). Иначе после деплоя старые записи до конца TTL читаются без ошибки, но с
  пустыми полями. Для независимого от домена формата нужен отдельный DTO с json-тегами.
- Все команды делят 128 MiB Redis без квот: активная команда может вытеснить списки остальных, и ключ может
  исчезнуть раньше 5 минут — это обычный промах. Попадание в кеш всё равно делает один небольшой
  SQL-запрос на членство и ревизию.

**Лимиты.** Лимит считается в памяти каждого процесса: несколько экземпляров не делят общий предел, после
перезапуска счётчики обнуляются. Общий лимит в Redis — возможное развитие, но локальный при этом должен
остаться: отказ Redis не должен снимать защиту.

**Логи.**
- Уровень логирования не настраивается: в коде зафиксирован `info`, переменной `LOG_LEVEL` нет. Для прода её
  нужно добавить (`debug|info|warn|error`) вместе с debug-записями, ради которых уровень опускают.
- SQL-запросы не логируются: в логах есть итог каждого HTTP-запроса (маршрут, статус, длительность) и текст
  непредвиденных ошибок базы, но не отдельные запросы. Для их анализа нужен либо slow/general log самого MySQL,
  либо логирование в приложении на уровне `debug` — текст запроса и длительность, без параметров, где есть
  email, хеш пароля и содержимое задач.

[^statuses]: Фиксированный набор статусов — упрощение первой версии. Дальше командам нужно дать собственные
    статусы и разрешённые переходы между ними; в этом API их нет.
