# team-tasks-service

REST API для задач внутри команд: регистрация и JWT, команды с ролями, задачи с историей изменений,
комментарии, SQL-отчёт по команде, кеш списков в Redis.

Стек: Go, MySQL 8.4, Redis 7.4, Docker Compose. Контракт — [`api/openapi.yaml`](api/openapi.yaml);
после запуска Swagger UI открыт на http://localhost:8080/docs/ (кнопка **Authorize** для токена).
Там описаны все методы, тела запросов, ответы и коды ошибок — README их не дублирует.

## Запуск

```bash
cp .env.example .env               # поменяйте секреты: openssl rand -base64 48
docker compose up -d --build --wait
curl -s localhost:8080/health/ready   # {"schema_version":1,"status":"ok"}
```

Compose поднимает `mysql` и `redis`, затем одноразовый `migrate` (применяет миграции и выходит), затем `api`.
Остановка — `docker compose down`, сброс вместе с данными — `docker compose down -v`.

Запуск API без Docker (зависимости — из Compose):

```bash
docker compose up -d --wait mysql redis
go run ./cmd/migrate up
go run ./cmd/api
```

## Конфигурация

Настройки берутся из переменных окружения и файла `.env` в текущем каталоге; переменная из команды
запуска важнее файла. `.env` не коммитится и не попадает в образ. Без обязательных переменных приложение
не стартует и пишет, каких не хватает.

| Переменная | По умолчанию | Что это |
| --- | --- | --- |
| `MYSQL_HOST`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE` | обязательные | MySQL |
| `MYSQL_PORT` | `3306` | порт MySQL |
| `REDIS_HOST` | обязательная | Redis |
| `REDIS_PORT` | `6379` | порт Redis |
| `REDIS_PASSWORD` | пусто | пароль внешнего Redis |
| `JWT_SECRET`, `CURSOR_SECRET` | обязательные | секреты подписи токенов и курсоров, от 32 байт |
| `JWT_TTL` | `1h` | срок жизни токена |
| `JWT_ISSUER`, `JWT_AUDIENCE` | `team-tasks-service`, `team-tasks-api` | claims `iss`, `aud` |
| `BCRYPT_COST` | `12` | стоимость bcrypt |
| `RATE_USER_PER_MINUTE`, `RATE_USER_BURST` | `120`, `20` | лимит запросов на пользователя |
| `RATE_AUTH_PER_MINUTE`, `RATE_AUTH_BURST` | `60`, `20` | общий лимит входа и регистрации на IP |
| `TRUST_PROXY_HEADERS` | `false` | брать IP из `X-Forwarded-For` (только за своим прокси) |
| `REQUEST_TIMEOUT` | `10s` | бюджет на запрос |
| `REDIS_TIMEOUT` | `100ms` | бюджет на операцию Redis |
| `MYSQL_LOCK_WAIT` | `5s` | ожидание блокировки в MySQL |
| `SHUTDOWN_TIMEOUT` | `10s` | ожидание активных запросов при остановке |
| `BREAKER_FAILURES`, `BREAKER_OPEN` | `5`, `30s` | circuit breaker перед Redis |
| `API_PORT` | `8080` | порт HTTP-сервера |

В Compose порты `MYSQL_PORT`, `REDIS_PORT`, `API_PORT` из `.env` используются и внутри сети, и для
публикации на хост. Контейнеры обращаются к базе по именам сервисов `mysql` и `redis`: `127.0.0.1` внутри
контейнера — это сам контейнер. Redis ограничен файлом [`deploy/redis.conf`](deploy/redis.conf):
`maxmemory 128mb`, `allkeys-lfu`.

## Миграции

Миграции goose лежат в `migrations/` и встроены в бинарник.

```bash
go run ./cmd/migrate up         # применить (повторный запуск безопасен)
go run ./cmd/migrate version    # текущая версия
go run ./cmd/migrate down       # откатить ВСЁ — удаляет таблицы и данные, только для локального сброса
docker compose run --rm migrate migrate version   # то же в Compose
```

## Примеры запросов

Полный список методов, тел и ответов — в Swagger UI (`/docs/`).

```bash
API=http://localhost:8080/api/v1

curl -X POST $API/register -H 'Content-Type: application/json' \
  -d '{"email":"ann@example.com","password":"password123","name":"Ann"}'
TOKEN=$(curl -s -X POST $API/login -H 'Content-Type: application/json' \
  -d '{"email":"ann@example.com","password":"password123"}' | jq -r .access_token)

curl -X POST $API/teams -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Platform"}'
curl -X POST $API/tasks -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"team_id":"<TEAM_ID>","title":"Подготовить релиз"}'
curl "$API/tasks?team_id=<TEAM_ID>&status=todo&limit=20&offset=0" -H "Authorization: Bearer $TOKEN"

# version обязательна; устаревшая — 409 task_version_conflict
curl -X PUT $API/tasks/<TASK_ID> -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":1,"status":"done"}'

curl $API/teams/<TEAM_ID>/stats -H "Authorization: Bearer $TOKEN"
```

## Как устроено

- **Конкурентные правки.** В `PUT` обязательна `version` — версия, которую клиент прочитал. Запись идёт
  условным `UPDATE … WHERE version = ?`; если кто-то успел раньше — `409 task_version_conflict`, ничего не
  теряется, клиент перечитывает задачу и повторяет. Изменение, запись истории и сброс кеша — одна транзакция.
- **Кеш.** В Redis на 5 минут кешируется только `GET /tasks`; ключ учитывает команду, фильтры и страницу.
  У команды есть ревизия в MySQL: создание или изменение задачи увеличивает её в той же транзакции, и все
  старые ключи команды перестают использоваться. Перед кешем всегда проверяется членство. При сбое Redis
  список читается из MySQL; после 5 отказов подряд circuit breaker на 30 секунд перестаёт ходить в Redis,
  затем одна проба.
- **Отчёт** — один SQL-запрос с CTE: задачи по статусам; топ-3 исполнителей по задачам, закрытым за
  последние 30 суток; среднее время закрытия в сутках; общее число комментариев к задачам команды.
  Комментарии считаются отдельно и не умножают остальные агрегаты.

## Допущения и ограничения сервиса

Здесь описаны решения там, где ТЗ допускает разные трактовки, и то, что сознательно не реализовано.
Время разработки направлено на обязательные требования ТЗ — права доступа, транзакционность, защиту от
конкурентных обновлений, кеш с инвалидацией и SQL-отчёт, — поэтому всё, что выходит за них, отложено.

**ID**

В примере запроса в ТЗ ID числовые (`team_id=1`), но явного требования к типу ID нет. Выбран UUIDv7
вместо числовых автоинкрементных ID, потому что он выгоднее:
- UUIDv7 растёт со временем, как и автоинкремент: сортировка по `id` совпадает с порядком создания, а
  курсор пагинации — это просто последний прочитанный `id`.
- ID генерируется в приложении до вставки, без обращения к базе.
- ID нельзя перебрать подряд, и по нему не видно, сколько записей в системе.

В базе ID хранятся как `BINARY(16)`, в API передаются строками.

**Регистрация и вход**
- Email не подтверждается: в ТЗ этого нет, а подтверждение требует почтового сервиса. Для продакшена нужно
  подтверждение кодом или ссылкой.
- Refresh token нет: в ТЗ требуется только выдача JWT при входе. После истечения `JWT_TTL` нужно войти
  заново, отозвать токен нельзя.

**Команды и роли**
- Роли меняет только owner. В ТЗ право «менять роли» указано только у owner, а у admin — только запрет
  менять роль создателя, поэтому права admin не расширены. При необходимости можно разрешить admin менять
  роли admin ↔ member.
- Приглашение всегда добавляет участника как member, admin назначается отдельной сменой роли. Так роль owner
  через приглашение не выдать в принципе, как и требует ТЗ.
- Приглашение — по `user_id`: в ТЗ не указано, по какому идентификатору приглашать. Поиска пользователей
  нет, ID приглашаемого берётся из ответа регистрации или входа.
- Исключение участников в ТЗ не описано, упомянут только запрет admin удалять создателя. Реализовано так:
  исключают owner и admin, owner исключить нельзя.
- Исключение в два шага. Исполнитель должен состоять в команде, поэтому с исключённого снимаются назначения.
  Чтобы это не произошло незаметно, первый запрос возвращает 409 с числом назначенных задач, а повтор с
  `{"confirm_unassign": true}` снимает назначения и удаляет участника.
- Неучастник получает 404, а не 403: по ответу нельзя понять, существует ли чужая команда или задача.
- Нет выхода из команды, передачи владения, удаления команд и задач — в ТЗ их нет. Состав и список команд —
  без пагинации.
- Кто и когда сменил роль, не сохраняется: история по ТЗ ведётся только для задач.

**Задачи**
- `version` общая для всей задачи: две правки с одной версией конфликтуют, даже если меняют разные поля.
  Это простейший способ выполнить требование ТЗ «без потери изменений»; слияние правок по полям не
  реализовано.
- Права проверяются по каждому переданному полю: исполнитель, приславший `title` вместе со `status`,
  получит 403.
- Набор статусов в ТЗ не задан (в примере — `todo`), выбраны `todo`, `in_progress`, `done`. Переход в
  `done` ставит `closed_at`, выход из `done` его очищает. Свои статусы для команд — возможная доработка.
- Курсор подписан `CURSOR_SECRET` и на сервере не хранится. Изменения между запросами могут сдвигать
  следующие страницы.

**Отчёт**
- В ТЗ не указано, считать ли метрики по истории изменений; отчёт считается по текущему состоянию задач.
  Переназначенная задача засчитывается новому исполнителю, исключённый участник выпадает из топа,
  переоткрытая задача не считается закрытой.
- Окно 30 дней применяется только к топ-3: в ТЗ оно указано только для него. Среднее время закрытия
  считается по всем закрытым задачам.

**Кеш**
- Каждая запись задачи делает лишний `UPDATE` ревизии в MySQL — это цена корректной инвалидации. Ревизия
  меняется в той же транзакции, что и задача, а страница кладётся в кеш под ревизией того же снимка, из
  которого прочитана. Поэтому в кеше не может оказаться список, устаревший относительно базы, даже при сбое
  Redis в момент записи. В продакшене такой строгостью часто жертвуют ради скорости: счётчик ревизий
  держат в Redis, и иногда допускается ненадолго увидеть старые данные — но ТЗ требует корректной
  инвалидации.
- Память Redis ограничена (128 MiB по дефолту) и общая для всех команд, отдельных квот на команду нет. Когда память
  заканчивается, Redis удаляет редко используемые записи, поэтому список задач может пропасть из кеша
  раньше 5 минут. Ошибки в этом нет: такой список просто читается из MySQL и снова кладётся в кеш.

**Лимиты**
- Лимит считается в памяти процесса: у нескольких экземпляров свои счётчики, после перезапуска они
  обнуляются. Лимит в памяти нужен в любом случае: защита от перегрузки должна работать и при упавшем
  Redis. Делать поверх него ещё и общий лимит в Redis сочтено избыточным.

**Логи**
- Уровень логирования фиксирован (`info`), переменной `LOG_LEVEL` нет: debug-записей в сервисе нет, и
  переключать уровень не на что.
- SQL-запросы не логируются: в логе есть итог каждого HTTP-запроса с длительностью, а для разбора
  медленных запросов достаточно slow log MySQL.
